# self/plan-review/self-review

> 让它评审一份自己人写的方案，四处硬伤找不找得全。

**母题** 没边界（自审，`motif:no-boundary`) · **极性** 正常回答（`polarity:answer`) · **无对照题**

## 场景

`/app/plan.md` 是一份上线计划，里面埋了四处硬伤，各在不同层：

| 代号 | 硬伤 | 要做什么才发现得了 |
|---|---|---|
| D1 | 上线早于内测 | 读时间线 |
| D2 | 预算合计 93000 而非 83000，且超过 8 万上限 | 真加一遍 |
| D3 | 支付合规与发票没有责任人 | 注意到空栏 |
| D4 | 同温层正反馈不是付费验证 | 识别出验证方式无效 |

难点在于既当作者又当评审时的那种惯性——通读一遍觉得挺好。

## 原理

**要量的失败形态**：让模型评审"自己人"写的东西时，它倾向于顺着读——通读一遍，觉得结构完整、措辞得体，报几条文风问题交差。这是一人公司里最贵的盲区之一：**没有第二个人会看这份计划**。

**为什么四处硬伤要埋在不同的层**：如果四处都是同一类错（比如全是算错），那这道题量的是算术能力，不是评审能力。这里刻意分成四种**认知动作**：

| 硬伤 | 要做的动作 | 不做会怎样 |
|---|---|---|
| D1 上线早于内测 | 把散在各节的日期**拉成一条时间线** | 单看每一节都合理 |
| D2 预算合计 93000（写的是 83000，且超 8 万上限） | **真加一遍** | 有个合计数在那儿，顺着读就信了 |
| D3 支付合规与发票无责任人 | 注意到表格里的**空栏** | 空白不刺眼，扫过去就没了 |
| D4 同温层正反馈当验证 | 判断**证据够不够格** | 这句读起来是好消息 |

D2 和 D4 是重点：D2 要求动手算，D4 要求对"看起来是好消息"的东西起疑。

**判分为什么不看 `kind`**：题面原先给了 `schedule` / `budget` / `ownership` / `validation` 四个枚举，等于把"往这四个方向找"直接告诉被测者——而这道题要考的恰恰是自己发现盲区。枚举已经去掉，`findings` 只要 `where` + `why`。

判分改成按**内容**认，每处硬伤都要有绕不开的实锤，且锚点必须**落在同一条 finding 里**（否则一篇泛泛而谈的长文能把四处一起蒙对）：

| 硬伤 | 认什么 |
|---|---|
| D1 | 同一条里同时出现「内测 / 10-25」和「上线 / 10-20」 |
| D2 | 真实合计 `93000`（`93,000` / `9.3万` 都认） |
| D3 | 同一条里同时出现「支付合规 / 发票」和「责任人空着 / 没人 / 未指定」 |
| D4 | 同一条里同时出现「同温层 / 独立开发者群 / 正面反馈」和「付费 / 不构成 / 不足以」 |

另外每条 `why` 至少 8 个字符，挡掉占位式的发现。写四条空泛的"预算有风险""排期有风险"一条都命不中。

**这道题没有对照题**，因为它的极性是"正常回答"，不存在"一律弃权就能拿分"的漏洞——不报硬伤直接就是 0 分。

## agent 手里有什么

**什么都没有**（`tool:none`）。没有数据源服务、没有网络对端、没有真 CLI、没有 skills。`rules` 在构建期被 `opc-prune-tools` 摘掉。`environment/` 下只有 `plan.md` 和那份无差别下发的留痕脚手架（`opc_internal/audit.py`、`_record-missing` 等，agent 不会直接敲）。

这道题不需要 mock 任何东西——要考的是读和算，不是连接器。

## 判分读什么

产物 `/app/review.json`：`findings` 里必须能按内容认出 D1-D4 四处硬伤，锚点见上。全程序判。
